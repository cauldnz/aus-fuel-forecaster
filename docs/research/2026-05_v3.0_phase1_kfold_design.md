## 1. Problem statement (why we're doing this)

The v2.x closing summary ([`2026-05_v2_closing_summary.md`](2026-05_v2_closing_summary.md)) identified the methodology gap that v3.0 exists to close: **single-split A-vs-B evaluation isn't robust enough to distinguish real wins from fold-specific noise.** The cleanest evidence sat in PR C's results — E1 wins test_normal, E4 wins test_crisis, E5 ("combine the wins") regressed both folds catastrophically, and the strongest single result (E4: test_crisis Δ MAE −0.603) cost meaningfully on test_normal (+0.151). With a single fold per evaluation period, we can rank but can't tell signal from noise.

This phase replaces the v2.x four-fold scheme (`train` / `val` / `test_normal` / `test_crisis`) with **time-series k-fold CV across the whole panel from 2017-01 to 2026-04**. The v2.x notion of a separate "crisis" fold is dropped — 2026 data is treated as ordinary time period and rotates into k-fold test windows alongside every other year. Each experiment reports per-fold Δ MAE + aggregate mean ± stdev in a single merged table; significance is judged by the spread of per-fold deltas, not by a p-value (per §2.5 reasoning).

The Docker handoff to remote training was originally part of this work but is **explicitly deferred** to v3.0 Phase 3 — Phase 1's goal is to get the harness working locally first. The user's laptop runs PR C's 7 experiments in ~5 hours at single-fit; at 6-fold CV that becomes ~30 hours per full re-evaluation pass. Bearable for one-off use, painful for iteration; Phase 3 solves the iteration cost.

## 2. Research synthesis — time-series CV state of the art

Three families of approaches dominate the time-series CV literature, with different trade-offs.

### 2.1 Walk-forward / expanding-window (the forecasting default)

Each fold's training set is everything before the test window; the test window is a contiguous chunk of subsequent dates. Training set grows with fold index ("anchored" or "expanding"). This is what `sklearn.model_selection.TimeSeriesSplit` implements ([scikit-learn issue #22523](https://github.com/scikit-learn/scikit-learn/issues/22523) — note that sklearn is currently limited to expanding only; rolling is a [feature request](https://github.com/scikit-learn/scikit-learn/issues/33520)).

- **Strength:** matches deployment (model is always trained on everything available at prediction time)
- **Weakness:** train size varies across folds — performance differences can reflect train size rather than model quality
- **Weakness:** later folds have implicit knowledge of regime shifts earlier folds didn't (e.g. a fold straddling 2022's Ukraine fuel price spike learns from data both before and after; an earlier fold doesn't)

The `gap` parameter ([sklearn docs](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html)) skips `gap` time-steps between train end and test start. **For h-step-ahead forecasting, gap must be ≥ h to prevent target leakage** (see §3.1).

### 2.2 Rolling / sliding window (fixed train size)

Train and test windows both have fixed width; both slide forward through time. Standard in financial backtest literature.

- **Strength:** train size constant across folds → fair like-for-like comparison
- **Strength:** adapts to regime change (early data falls off when no longer relevant)
- **Weakness:** discards data on later folds — less efficient use of long histories
- **Weakness:** doesn't match deployment (where you'd use all history)

Per the [mlxtend `GroupTimeSeriesSplit` docs](https://rasbt.github.io/mlxtend/user_guide/evaluate/GroupTimeSeriesSplit/), sklearn's `TimeSeriesSplit` doesn't support this natively — third-party libraries or custom implementations needed.

### 2.3 Purged k-fold with embargo (López de Prado)

Introduced in [López de Prado (2018), *Advances in Financial Machine Learning*](https://reasonabledeviations.com/notes/adv_fin_ml/); see also the [purged cross-validation Wikipedia page](https://en.wikipedia.org/wiki/Purged_cross-validation) and [Grokipedia article](https://grokipedia.com/page/purged_cross_validation). Standard random k-fold + two corrections:

- **Purge:** drop training samples whose label-derivation window overlaps the test window. For us: if `y_t1[D]` is computed from `price[D+1]`, and D+1 is in the test set, the train row at D must be dropped (otherwise its target = a test row).
- **Embargo:** add a buffer period after each test fold before the next training fold can begin. Prevents feature engineering on the next train fold from drawing on test data via lag/rolling computations.

[Antonio Velazquez Bustamante's walkthrough](https://antonio-velazquez-bustamante.medium.com/kfold-cross-validation-with-purging-and-embargo-the-ultimate-cross-validation-technique-for-time-2d656ea6f476) is the most accessible practical guide. Reference implementations exist (e.g. [sam31415/timeseriescv](https://github.com/sam31415/timeseriescv/blob/master/timeseriescv/cross_validation.py)).

- **Strength:** principled handling of label-overlap leakage that simpler schemes miss
- **Strength:** every fold has same train + test geographic / distribution mix (random splits)
- **Weakness:** random splitting breaks chronology — train rows can be FROM AFTER the test window, which doesn't reflect deployment for a forecasting problem
- **Useful subset:** even when staying chronological, the **embargo** idea is straightforwardly useful for cross-fold feature-engineering leakage

### 2.4 What works for fuel-price prediction (where we land)

The forecasting-friendly default is **expanding-window with gap**. Reasoning:

- We deploy as a forecaster: at prediction time we have all past history, so train growth across folds is the right deployment-matched approach
- Rolling-window's "adapts to regime change" benefit doesn't help us — we WANT the model to see the 2020 / 2022 shocks so it can generalise to 2026's crisis
- Purged k-fold's random splitting violates chronology, which for forecasting is a critical invariant
- The embargo concept from purged k-fold is worth borrowing: gap = max(target_horizon, lag_window_depth) handles both target leakage AND rolling-feature carry-over

So: **chronological expanding-window k-fold with gap = max(1, 28) = 28 days**, leaving room to reason about the embargo edge cases (§3).

### 2.5 Per-fold significance testing

The classic [Dietterich (1998) result](https://pages.cs.wisc.edu/~jerryzhu/cs769/ttest.pdf) is that the standard paired t-test on k-fold cross-validated scores has **inflated Type I error** because the per-fold scores aren't independent — every observation appears in (k-1) training folds. [MachineLearningMastery's guide](https://machinelearningmastery.com/statistical-significance-tests-for-comparing-machine-learning-algorithms/) covers the corrections. Two main alternatives:

- **5×2cv paired t-test** (Dietterich, implemented in [mlxtend](https://rasbt.github.io/mlxtend/user_guide/evaluate/paired_ttest_5x2cv/)): 5 repetitions of 2-fold splits. Designed for IID data; doesn't fit time-series cleanly because you can't 2-fold split a chronological sequence.
- **Nadeau-Bengio corrected t-test**: variance correction for fold dependence. Applicable to time-series CV but adds complexity.

**Decision: don't compute p-values.** Per-fold reporting + mean ± stdev is more honest. If a change moves the headline by 0.5 c/L and the per-fold stdev is 0.05 c/L, it's a real effect. If the change moves the mean by 0.05 c/L and the stdev is 0.2 c/L, the spread tells you "noise". The user judging by eye is more defensible than a p-value calculation that requires assumptions we don't quite meet.

The reference: [arxiv.org/abs/2512.06932 on hidden leaks in time-series forecasting](https://arxiv.org/html/2512.06932v1) shows that even sophisticated significance testing is dominated by leakage controls — getting the splits right matters far more than which test you use.

## 3. Leakage in OUR pipeline — what to defend against

Generic time-series CV advice ([hectorv.com on data leakage](https://hectorv.com/2023/07/06/data-leakage-in-time-series-data-cross-validations-in-machine-learning/), [Medium guide on respecting order](https://medium.com/@pacosun/respect-the-order-cross-validation-in-time-series-7d12beab79a1)) covers leakage classes; this section maps them to our specific code paths.

### 3.1 Target leakage from the `y_t1` shift (REAL — needs gap-fold)

`build.make_features.add_targets` constructs:

```python
y_t1 = df.groupby(["station_id", "fuel_code"])["price_mean"].shift(-1)
```

So a row at date D has `y_t1 = price_mean[D+1]`. If train_end = D and val_start = D+1, the last train row's target is *the val period's first price*. **The current v2.x setup has this 1-day leak today** — train_end is 2022-12-31, val_start is 2023-01-01, and the last train row has `y_t1 = price[2023-01-01]`. It's a small leak (1 row × ~5000 stations = ~5000 rows worth of leaked information out of ~5M train rows) but it's there.

**Fix:** introduce a `gap_days` parameter on the fold splitter. For `y_t1` (1-day horizon), `gap_days = 1` is sufficient. For `y_t1_t7` (7-day mean horizon), `gap_days = 7`. Train rows where `date + horizon > test_start - gap` get dropped.

### 3.2 Rolling-feature leakage across the train/test boundary (NOT REAL — same as deployment)

`add_lag_features` computes rolling means/stds within `(station_id, fuel_code)` groups via `s.shift(1).rolling(28, min_periods=28).mean()` etc. For a test row at date D, `roll_price_mean_28` is the mean of `price[D-28..D-1]` — which includes train-period values. **This is not leakage** — at deployment time the model would have exactly the same set of past prices available.

The `min_periods=28` guard prevents early-life nulls but isn't a leakage defence per se. Pre-spec §7.1 comment to this effect.

### 3.3 Forward-fill leakage in macro features (NOT REAL — already past-only)

`add_upstream_features` forward-fills Brent / AUDUSD across weekends/holidays:

```python
brent_d = brent.assign(date=...).sort_values("date").ffill()
```

`ffill()` propagates the LAST KNOWN value forward (past → future). A weekend gap in brent at D would be filled from D-1, never D+1. **Not leakage** — the deployed model would do the same.

### 3.4 Augmentor temporal-mode leakage (NOT REAL — release resolution is row-date-driven)

In PR B's `build.enrich_panel_temporal`, each (station, date) row resolves to the SEIFA / ERP release whose publication date is closest-at-or-before the row's date. A train row at 2018-06-15 gets 2016 SEIFA; a test row at 2024-06-15 gets 2021 SEIFA. The augmentor's release lookup uses the row's own date — never future dates. **Not leakage.**

One subtle thing: `temporal.out_of_range='nearest'` clamps pre-earliest-release rows to the earliest release (e.g. 2018-06-15 DSS rows clamp to 2022-Q4). This means *train* rows get values from a *post-train-period* publication. Strictly speaking, the v1.5 vintage SEIFA "knew" about post-train-period statistics. We accept this — the alternative is to embargo the augmentor too, which would make most of the train fold null on DSS. The closing summary's recommendation to keep DSS cross-sectional (latest quarter only) lives in the same camp.

### 3.5 Embargo for rolling features at the upper boundary (REAL — needs gap)

Symmetric to §3.1: if val_end = D and test_start = D+1, the test row at D+1 has `lag_price_1 = price[D]` which is a val-period price. Same logic applies as §3.2 (this is what deployment would do, not leakage). **But**: if our k-fold rotates the test window, and a subsequent fold's TRAIN includes the rows that were the previous fold's TEST, then those train rows' rolling features were computed including their own future. That's a real concern only when the same row appears in both train and test across folds — which DOESN'T happen in chronological k-fold (each row appears in exactly one test fold, and in the train fold of every later fold).

For the chronological expanding-window scheme we're using: **no embargo needed beyond gap_days = max(target_horizon, 0) = 1.**

### 3.6 The categorical-coercion side effect (NOT REAL but watch it)

`train.train_models._coerce_categorical_union` builds a shared category set across train + val + every test fold. The categories include all unique values across the whole feature matrix. For nominal columns (e.g. `stn_brand_canonical`) this is benign. For an ordinal that's computed from data (e.g. some quantile-binned feature) this could be a leak — but we don't have any such columns. **Confirm before each Phase 2 re-eval.**

### 3.7 Summary table

| Leakage class | In our code? | Fix |
|---|---|---|
| Target shift (`y_t1`) | Yes — train row at D has y = price[D+1] | `gap_days = horizon` |
| Rolling/lag features straddling boundary | Yes by construction | None — same as deployment |
| Forward-fill of macros | No — `ffill()` is past-only | n/a |
| Augmentor temporal release lookup | No — row-date-driven | n/a (clamp to earliest is documented compromise) |
| Embargo for repeated rows | No — chronological folds | n/a |
| Categorical-set computed from full data | Benign for our cols | Re-verify each Phase 2 PR |

## 4. Decisions table

All decisions confirmed in the 2026-05-31 planning session (locked answers to what was previously §8 open questions).

| Decision | Choice | Rationale |
|---|---|---|
| CV scheme | **Expanding-window chronological** | Matches deployment; rolling-window's regime-adaptation benefit doesn't fit our use case |
| Fold count (k) | **6** | Standard 6-10 range; 6 keeps wall-clock to ~6× single-fit while still giving 6-point mean/stdev |
| Test fold width | **12 months** | Each test window covers a full year so per-fold MAE is averaged over enough seasonal variation to be stable |
| Panel coverage | **Whole panel 2017-01 → 2026-04 covered by rolling test windows** | All of 2025 + 2026 rotate through as test data; nothing held out as "future buffer" |
| `gap_days` between train and test | **1** for `y_t1` | Smallest gap that prevents target leakage. Matches §3.1 analysis. Override via `FoldConfig.gap_days` |
| Crisis as a separate concept | **Dropped entirely** | The v2.x distinction between `test_normal` and `test_crisis` is gone in v3.0. 2026 is just another time period in rotating CV. Spec §15.3 calls this out explicitly; spec §8.3 marks the v2.x scheme as deprecated |
| Val fold within each CV fold | **Last 365 days of the train portion** | Standard expanding-CV pattern: val carved out of the most-recent train slice so LightGBM early stopping sees recent-enough data to generalise. `n_estimators` cap honoured per fold |
| Per-experiment reporting | **Single merged table** | Per-fold rows + aggregate row(s) (mean ± stdev, min, max) in one comparison.md table. No separate "OOD" line — crisis-as-separate is gone |
| Significance judgement | **Eyeball: mean vs stdev** | If mean Δ ≫ stdev, robust. If similar, fold-specific noise. No p-values (see §2.5) |
| Identical-rows guard | **Per-fold** | Each fold computes its own "rows where SA2 cols are non-null"; Model A/B/B' train on identical filtered set within that fold |
| Categorical-set | **Recomputed per fold** | A category present in fold N's train but absent in fold M's train shouldn't break model M. Each fold's coercion uses its own union |
| Embargo (beyond gap) | **None — gap is sufficient** | §3.5 analysis: chronological folds don't have the repeated-row-across-folds problem that motivates embargo |
| Aggregate metric direction | **Negative Δ = Model B beats A** | Unchanged from v2.x convention |
| Storage layout | `models_kfold_<experiment>/fold_N/{model_a,model_b,model_b_prime}.pkl` + `predictions_fold_N.parquet` | One subdir per fold; aggregation reads from these |

### 4.1 Concrete fold geometry (k=6, 12-month windows ending at panel last date 2026-04)

The 12-month-test rule + need to cover all of 2025 + 2026 forces a non-calendar-aligned geometry. Test windows roll month-by-month: the last fold's test ends at the panel boundary (2026-04-30), and earlier folds back off by 12 months each. This keeps every fold's test window exactly 12 months while covering the full target span.

| Fold | Train window | Val window (last 365d of train) | Test window |
|---|---|---|---|
| 1 | 2017-01-01 → 2020-04-30 | 2019-05-01 → 2020-04-30 | 2020-05-01 → 2021-04-30 |
| 2 | 2017-01-01 → 2021-04-30 | 2020-05-01 → 2021-04-30 | 2021-05-01 → 2022-04-30 |
| 3 | 2017-01-01 → 2022-04-30 | 2021-05-01 → 2022-04-30 | 2022-05-01 → 2023-04-30 |
| 4 | 2017-01-01 → 2023-04-30 | 2022-05-01 → 2023-04-30 | 2023-05-01 → 2024-04-30 |
| 5 | 2017-01-01 → 2024-04-30 | 2023-05-01 → 2024-04-30 | 2024-05-01 → 2025-04-30 |
| 6 | 2017-01-01 → 2025-04-30 | 2024-05-01 → 2025-04-30 | 2025-05-01 → 2026-04-30 |

Notes:
- 2016-09 → 2016-12 is excluded from all train windows — used as lag-feature warmup only (4 months covers `lag_price_28` + `roll_price_mean_28` warmup)
- `gap_days=1` means each train window's last date is `test_start - 2` (one day for gap, dropped target row dropped explicitly). Implemented at split time, not as a post-filter
- Both 2025 and 2026 are covered as test data: fold 5's test ends 2025-04-30, fold 6's test starts 2025-05-01 and runs through 2026-04-30 (the panel's end). No date in [2017-01, 2026-04] appears in more than one test fold; every date in that range appears in exactly one
- Fold 1's train (~40 months) is the shortest; fold 6's train (~100 months) is the longest. This is intrinsic to expanding-window and the right deployment match — we want the late-fold model to know about all prior history

## 5. Implementation plan

### 5.1 Module surface

**`src/fuel_pred/train/folds.py`** — extend, don't rewrite:

- Keep `FoldConfig` + `split_folds` + `FoldMap` as the single-split path (used by `train.train_models.train` today; Phase 1 doesn't break this)
- Add `KFoldConfig` dataclass with: `k`, `test_window_months`, `val_window_months`, `gap_days`, `warmup_end` (date strings), `panel_end` (date string), `crisis_start` / `crisis_end` (date strings)
- Add `split_kfolds(df, *, kfold_config)` returning a list of `FoldMap` (length k); each `FoldMap` has `{"train", "val", "test"}` keys + optionally `"crisis"` on the last fold
- Add `KFoldConfig.default()` returning the §4.1 geometry

**`src/fuel_pred/train/cv.py`** — NEW, owns the k-fold loop:

- `train_kfold(features_path, out_dir, *, kfold_config=None, ...)` — for each fold N, calls a refactored `_train_single_fold(...)` that fits A/B/B' on the fold's (train, val) and predicts test (+ crisis on fold 6)
- Returns a `KFoldResult` dataclass with per-fold `FitResult` + per-fold predictions paths
- Writes `models_kfold_<exp>/fold_N/` per fold

**`src/fuel_pred/train/train_models.py`** — refactor:

- Extract a private `_train_one_fold(train_df, val_df, test_dfs, *, fit_params, weather_source, log_period) -> dict[fold_name, FitResult]` that's the inner loop
- `train()` becomes a thin wrapper: load features, single split, call `_train_one_fold` with the 4 folds
- `train_kfold()` (in `cv.py`) is a wrapper: load features, k-fold split, call `_train_one_fold` per CV fold

**`src/fuel_pred/evaluate/compare.py`** — extend:

- Keep current `compare(features_path, models_dir, out_path)` for the single-split path
- Add `compare_kfold(features_path, kfold_models_root, out_path)` that:

  - Loads per-fold predictions

**`Makefile`** — new target:

- `train-kfold:` — same dependency chain as `train` but invokes `python -m fuel_pred.train.cv ...`
- `evaluate-kfold:` — paired with `evaluate.compare_kfold`

## 6. Smoke milestone — reproduce PR B baseline under k-fold

The first end-to-end run before opening the PR. Validates the harness, doesn't claim any model improvement.

1. Run `python -m fuel_pred.train.cv --features data/processed/features.parquet --out models_kfold_pr_b_smoke` against the committed v2.x feature set (no config changes)
2. Run `python -m fuel_pred.evaluate.compare_kfold --models-root models_kfold_pr_b_smoke --out results/v3_pr_b_smoke_kfold.md`
3. Verify that fold-by-fold Δ MAE is reported across the 6 windows, plus an aggregate row with mean ± stdev. There's no clean apples-to-apples comparison to the v2.x single-split headline because:
   - v2.x `test_normal` (2024-01 → 2025-12) crosses two v3.0 fold boundaries (fold 5 ends 2025-04, fold 6 starts 2025-05). The closest single fold to v2.x's `test_normal` is fold 5 (test 2024-05 → 2025-04), which roughly overlaps but isn't identical.
   - v2.x `test_crisis` (2026-01 → 2026-04) is now contained inside fold 6's test window (which extends back to 2025-05). Per-fold MAE on fold 6 averages over a wider window than v2.x's crisis-only number, so the direct comparison is misleading.
4. **Real sign-off criterion:** the harness produces sensible per-fold + aggregate output, no NaNs in unexpected places, the gap-days fix is observably applied (count of dropped rows logged per fold), and the mean ± stdev across folds is informative (e.g. stdev < |mean| means the headline is genuinely above noise; stdev ≫ |mean| would tell us the v2.x PR B signal might itself have been fold-specific).
5. Report the per-fold mean ± stdev as the first v3.0 baseline number. **This is itself a v3.0 finding** — whether the PR B "Model B beats Model A" claim holds across all 6 folds or only at the specific 2024-25 window the v2.x scheme happened to use.

The v3.0 baseline replaces v2.x's `−0.239` / `−0.321` headline pair with a single mean ± stdev across 6 folds (no separate crisis number).
